# 初期プロトタイプの内部形式

この文書は現在の実装を説明する。合意した将来の仕様は[design.md](design.md)を参照。現在の形式は初版（形式バージョン1）で、公開までは互換性を持たせずにこの版のまま変更する。形式バージョンが1でないプロジェクトは開かない。

## ファイル構成

```text
project/
  project.json
  data/<import UUID>/
    metadata.e57
    source.xml                 # E57取り込み時のみ
    <dataset UUID>.points
    <dataset UUID>.view        # 表示用8分木の点
    <dataset UUID>.scan.json   # スキャンのメタデータ（チャンク・表示用8分木）
  labels/<patch UUID>.labels   # 点の所属レイヤー（ラベルパッチ）
  labels/<patch UUID>.json     # ラベルパッチのメタデータ
  staging/
```

パスはプロジェクトルートからの相対パス。入力の絶対パスは動作に必要ない。`metadata.e57`は0点のスキャンschemaとメタデータ、および元の画像を保存する。原解像度点の二重保存はしない。

`project.json`には名前、画像情報、リビジョンと作業状態、スキャンとラベルパッチのメタデータファイルへの相対パスを記録する。スキャン（チャンク・表示用8分木を含む）とラベルパッチのメタデータは、作成後に変わらないため別ファイルにし、まだファイルがないものだけを保存時に書く。編集のたびに書き直すのは小さな`project.json`だけになる（Trimbleの848万点で約0.5 MBから約3 KBに減った）。読み込み時はファイル名とメタデータの対応を確かめる。

メタデータ全体はRAMに保持する。ファイルは一時ファイルを同期してから置換するため、途中で止まっても半端な内容は残らない。複数プロセスからの書き込み排他はまだない。

## 点レコード

展開後の`.points`はリトルエンディアンの固定長レコード列。各スキャンの`stride`でサイズを指定する。ディスク上はチャンクごとの独立したブロックで、メタデータに`offset`、`stored_bytes`、`codec`を記録する。

`zstd_shuffle`ブロックは、同じbyte位置を全点から集めた列に可逆転置し、Zstd level 1の独立フレームで圧縮する。フレームのチェックサムを有効にする。点順序もIEEE浮動小数点のbit列も変えない。圧縮で容量が増えるブロックは`raw`で保存する。展開サイズは点数とstrideから計算し、最大32 MiBに制限する。

| オフセット | サイズ | 内容 |
| ---: | ---: | --- |
| 0 | 24 | 描画・計算用ローカルXYZ、f64×3 |
| 24 | 4 | 描画用RGBA、u8×4 |
| 28 | 1 | 座標が有効なら1、無効なら0 |
| 29 | 3 | 予約領域 |
| 32 | schemaによる | 元の数値属性、prototype順 |

元の属性はSingleをf32、Doubleをf64、IntegerおよびScaledIntegerをi64で保存する。ScaledIntegerはscale適用前の整数を保存し、scale/offsetはE57 templateから復元する。属性の削除・量子化は行わない。球面座標は描画用XYZに変換しても、元の球面属性を別に保持する。座標無効レコードは表示しないが、表示中のレイヤーにあれば書き出す。

チャンクはファイルのbyte offsetと点数で参照する。一度作った原解像度点は編集で更新せず、`PointRef = (dataset UUID, chunk index, index in chunk)`を暗黙の識別子として使用する。

LAS/LAZでは現在保持するXYZ・強度・RGBからE57用schemaを作る。その他のLAS属性の保持は別途実装が必要。

## 処理用チャンクと表示用8分木

点群は、処理用の原解像度チャンクと、表示用の8分木の2つで持つ。2つは点参照でつながる。

### 処理用チャンク

入力をストリーミングで一時ファイルに書き、外部メモリの再帰的8分割で空間チャンクへ再配置する。分割ごとに中間ファイルを処理し、チャンクが点数・byte数の上限（既定65,536点・32 MiB）に収まったら確定する。同一点の大量重複や分割深度の上限では、一定点数のファイル区間に分ける。各チャンクは処理用8分木の葉で、点数は上限以下で大きくばらつく。

### 表示用8分木

Potree 2と同じ足し算型の8分木。有効な点はすべて、どれか1つのノードにちょうど1回だけ入る（無効点は入らない）。親と子を同時に描いても二重にならず、上位から順に足すだけで密度が上がる。

- 上の部分は処理用8分木と同じ形で、その葉（チャンク）の下を、ノードの点数が`ImportOptions.view_leaf_points`（既定16,384）以下になるまで箱の中心でさらに8分割する。深さは処理用チャンクの大きさで止まらない。
- 葉のノードは自分の点をすべて持つ。それ以外のノードは、子が持つ点から、ノードの箱の最長辺を`ImportOptions.view_grid`（既定128）分割した立方格子のセルごとに、セル中心に最も近い1点（同じならチャンク番号・点番号の小さい点）を選んで子から取り上げる。面の点群なら1階層あたり約4倍ずつ密度が上がる。
- ノードの箱は、そのノードと子孫の点にぴったり合わせる。
- 点の座標は元の点と同じf64で持つ。表示点で判定する選択プレビューを、原解像度で判定する確定結果とbit単位で一致させるため。

`.view`は、ノードごとに独立したブロック（点と同じbyte shuffle + Zstd）を並べたファイル。展開後の1レコードは36 byte。

| サイズ | 内容 |
| ---: | --- |
| 4 | chunk index、u32 |
| 4 | index in chunk、u32 |
| 24 | ローカルXYZ、f64×3 |
| 4 | RGBA、u8×4 |

スキャンのメタデータの`nodes`が表示用8分木で、ノード0が根。各ノードは箱、子、自分の点数、`offset`・`stored_bytes`・`codec`、チャンクごとの点数（`chunks`）を持つ。`chunks`から、ラベルを読まずにノードの表示中の点数を見積もれる。Trimbleの848万点では、点データ203 MBに対し`.view`は111 MB（以前の代表点LODは17 MB）。

### 並列取り込み

PotreeConverterのタスクプールと書き込み待ち量の制御を参考に、E57の点属性変換、チャンクの圧縮、チャンクの下の表示用部分木の構築を並列化している。新しい外部依存は追加せず、Rust標準ライブラリのスレッドとchannelを使用する。既定は利用可能CPU数−1、最小1・最大8ワーカー。`ImportOptions.worker_threads`で1〜64を明示指定でき、0は自動選択。

E57の読み出しは一つのreaderで行い、最大8,192点のraw値バッチをワーカーへ渡す。ワーカーが元の数値属性と描画用XYZ/RGBAを変換し、取り込み順に一時ファイルへ書く。複数スキャンの処理、E57の圧縮データ読み出し、LAS/LAZの点読み出しは引き続き直列。

空間分割は順序を管理するスレッドで行い、チャンク番号を確定してからワーカーへ渡す。各ワーカーがチャンクの圧縮と、チャンクの下の表示用部分木の構築・圧縮を行う。部分木の根に残った点は、親が選ぶまで一時ファイルに置く。完成ブロックは投入順に一つのwriterへ書き、部分木のノード番号は処理用8分木のノードの後に投入順で振るため、同じ取り込み設定ならワーカー数で点順序・点参照・表示用8分木は変わらない。

処理中の入力、圧縮scratch、結果バッファーに見積もり容量を予約し、既定256 MiBの`worker_memory_bytes`と最大`2 × ワーカー数`の投入件数で制限する。完成済み結果もwriterが取得するまで予約を維持する。予算が小さい場合はrawバッチを小さくし、極端に属性の多い点では原解像度チャンクも予算に収まるまで小さくする。予約はアクティブなワーカー用変換バッファーの上限であり、アプリ全体のRAM上限ではない。reader・Zstd内部状態、スレッドstack、allocatorの保持領域、manifest、表示キャッシュなどは別途使用する。

全チャンクの後、処理用8分木の内部ノードを下から上へたどり、各ノードで子の根に残った点を一時ファイルから読んで格子で選ぶ。選ばれなかった点はその子の点として書き、選んだ点は一時ファイルに置いて親を待つ。RAMに置くのは1ノードの子の点だけ。この段階は直列で、分割の一時ファイルI/O削減と空間サブツリー単位の並列化は今後の改善候補。Trimbleの848万点の取り込みは約7.6秒で、表示用8分木の導入前とほぼ同じ。

ワーカー待ちは50msごとにキャンセルを確認し、終了時には未開始タスクを破棄して動作中のワーカーをjoinする。属性変換・分割・表示用8分木の構築にもキャンセル確認を入れている。Zstd呼び出しは一つの最大32 MiBブロックを完了してからキャンセルを確認する。取り込みの確定は全ワーカー完了後なので、途中キャンセル・ワーカーエラーでは元のリビジョンを維持する。キャンセルされたstaging資産は既存の方針どおり残る。

参照した箇所は`ref/PotreeConverter/Converter/src/chunker_countsort_laszip.cpp`の入力バッチ処理、`src/indexer.cpp`のチャンク単位処理と下から上への点の選び直し、`include/ConcurrentWriter.h`の書き込み待ち容量制御。

### 表示

Potreeと同じ方式。表示要求ごとに、表示中のスキャンの根を優先度キューに入れ、画面上で大きいノード（箱の半径÷視点からの距離、平行投影では表示範囲で割る）から順に取り出す。視錐台の外のノードと、表示中のレイヤーの点が子孫まで含めてないノードは入れない。取り出したノードの表示中の点数の見積もりを足すと描画点数を超えるところで止める。取り出したノードが画面上で十分大きい（半径÷距離が0.015を超える）ときだけ子を入れる。描画点数が根の合計より小さいときは、各根を点数に比例して等間隔に間引く。

表示ワーカーは、選んだノードのうちキャッシュにあるものをすぐ返し、残りを優先度の高い順に読む。読み込み中も40msごとに読めた分を送る。新しい要求（カメラの移動）が来たら読み込みを打ち切ってやり直すが、読んだノードはキャッシュに残る。移動中も描画点数を減らさない。

ノードの点は、展開と非表示レイヤーの点の除外を済ませ、スキャンのローカル座標でLRUキャッシュに保持する。上限はPotreeの`pointLoadLimit`と同じく描画点数の2倍の点（1点40バイト）。カメラやスキャンの変換だけが変わったときは再利用し、プロジェクト、適用するラベルパッチの一覧、表示中のレイヤーの集合のどれかが変わると無効化する。チャンクごとの非表示点のマスクも同じ期間キャッシュする（根に近いノードは多くのチャンクの点を持つため）。

GPUにはノードごとの頂点バッファー（位置をノードの最初の点からのf32の相対座標、色をu8×4で1点16 byte）と、選択プレビューの印（1点4 byte）を常駐させる。描画時にスキャンのワールド行列とノードの原点をf64で合成してから単精度にするため、大きな座標でも精度が落ちない。スキャンの変換、位置合わせのプレビュー、スキャンごとの色分けは行列とuniformだけで反映し、読み直さない。新しいノードの転送は1フレーム200万点までとし、残りは次のフレームに回す。GPUのノードも描画点数の2倍の点を上限に、最近描いていないものから捨てる。

848万点のTrimbleを描画点数2000万で表示する場合（実際には約650万点を描く）、以前は視点を動かすたびに全点の作り直しで約2.0秒かかっていた。現在は初回の読み込みが約0.63秒、キャッシュ済みの範囲で視点を動かしたときの読み直しは数ms。

点を非表示のレイヤーへ移しても表示用8分木は作り直さない。表示の予算は表示中の点数の見積もりで数えるため、大きく減ったスキャンも深い階層まで描く。

## レイヤー、pose、リビジョン

すべての点はちょうど一つのレイヤーに属する。レイヤーは状態（リビジョン・作業状態）ごとの`layers`に、番号`code`（u8）・名前・表示の有無として記録する。番号0は既定のレイヤーで、常に存在し、改名・削除できない（名前`Points`は画面では「点群」と表示する）。新しいレイヤーには未使用の最小の番号を割り当てる。表示中のレイヤーの点だけを表示・選択・フィルター・位置合わせ・書き出しの対象とし、どのレイヤーにも定義されていない番号の点は非表示として扱う。

点の所属は、チャンクごとに点1つにつき1 byteのレイヤー番号の配列（ラベル）で持つ。`.labels`はラベル配列をチャンクごとに独立したZstd level 3のフレーム（チェックサム付き）で並べたファイルで、その`.json`（ラベルパッチ）がdataset UUID・chunk index・byte offset・長さと、既定以外のレイヤーごとの点数を、スキャン・チャンクの順に持つ。全点が既定のレイヤーに戻ったチャンクは長さ0のブロックとして記録し、配列を持たない。

状態の`labels`は適用するラベルパッチのUUIDを適用順に並べる。チャンクのラベルは、一覧を後ろから見て最初にそのチャンクを含むパッチの配列とし、どのパッチにもないチャンクは全点が既定のレイヤーにある。ラベルパッチは一度書いたら変更しない。点を移す操作（範囲選択、3Dボックス選択、間引き、ノイズ除去、SOR、レイヤー全体の移動・削除）は、所属が変わったチャンクだけの新しい配列を一つのパッチとして`staging/`に書き、`labels/`へ移してから作業状態の`labels`に追加する。何も動かなかった操作は状態を変えない（レイヤーの削除だけは、点がなくてもレイヤーの定義を外す）。操作が新しく作るレイヤーは非表示で始まり、ユーザーが作るレイヤーは表示で始まる。

チャンクごとのレイヤー別点数はパッチのメタデータにあるため、どのチャンクに非表示の点があるか、レイヤーごとの総点数、表示の描画枠に使う残存割合は、ラベル配列を読まずに求める。非表示の点がないチャンクのラベルは読まない。

操作の記録（`operation`の各要素）には、点を移した操作では移動先のレイヤー番号`target`と移した点数`moved`を加える。

各リビジョンは親ID、対象スキャンID、レイヤーの定義、適用するラベルパッチのID、追加剛体変換、フォルダー（`groups`: ID・名前・親フォルダー）、スキャンの所属フォルダー（`scan_groups`）、操作内容、保存日時（`saved_at`、Unix秒）を持つ。`transforms`はスキャンとフォルダーの両方の追加変換を持ち、スキャンの世界座標は「上位フォルダーから順の変換 × スキャン自身の変換 × スキャンpose × ローカル座標」で求める。

編集は`manifest.draft`（未保存の作業状態）だけを変更し、編集ごとに`project.json`へ書き込む。作業状態は保存済みリビジョン`current`を親とし、編集ごとに新しいIDを持つ（表示キャッシュとプレビューの鍵）。`operation`は`{"kind":"edits","operations":[...]}`で、編集の記録を順に持つ。ユーザーが保存すると作業状態をそのままリビジョンとして追加し、`current`にする。リビジョンを切り替えると作業状態を破棄する。元に戻す・やり直すは、作業状態のスナップショットを差し替えるだけで、点・表示用8分木・ラベルは書き換えない。

取り込みと点の移動は新しい資産を書き終えてから作業状態を更新する。保存に失敗した資産やキャンセルされた作業は未参照のまま残り、「履歴のクリーンアップ」（`Project::cleanup`）で削除する。クリーンアップは保存済みリビジョンと作業状態のどれからも参照されないスキャン・画像情報・ラベルパッチをメタデータから外して保存した後、`data/`の未参照の取り込みディレクトリと未参照の`.points`・`.view`、`labels/`の未参照のパッチ、`staging/`の中身、中断された保存の一時ファイルを削除する。途中再開、複数リビジョンの集約、積み重なったパッチを一つにまとめる処理は未実装。

スキャンの世界座標は`追加変換 × 元のscan pose × ローカル点`。対応画像は`追加変換 × 元のimage pose`で書き出す。画像をスキャン原点と同一視せず、複数カメラの異なるposeを保持する。
