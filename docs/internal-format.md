# 初期プロトタイプの内部形式

この文書は現在の実装を説明する。合意した将来の仕様は[design.md](design.md)を参照。現在の形式は初版（形式バージョン1）で、公開までは互換性を持たせずにこの版のまま変更する。形式バージョンが1でないプロジェクトは開かない。

## ファイル構成

```text
project/
  project.json
  data/<import UUID>/
    metadata.e57
    source.xml                 # E57取り込み時のみ
    <dataset UUID>.points
    <dataset UUID>.lod
    <dataset UUID>.scan.json   # スキャンのメタデータ（チャンク・空間ノード）
  labels/<patch UUID>.labels   # 点の所属レイヤー（ラベルパッチ）
  labels/<patch UUID>.json     # ラベルパッチのメタデータ
  staging/
```

パスはプロジェクトルートからの相対パス。入力の絶対パスは動作に必要ない。`metadata.e57`は0点のスキャンschemaとメタデータ、および元の画像を保存する。原解像度点の二重保存はしない。

`project.json`には名前、画像情報、リビジョンと作業状態、スキャンとラベルパッチのメタデータファイルへの相対パスを記録する。スキャン（チャンク・空間ノードを含む）とラベルパッチのメタデータは、作成後に変わらないため別ファイルにし、まだファイルがないものだけを保存時に書く。編集のたびに書き直すのは小さな`project.json`だけになる（Trimbleの848万点で約0.5 MBから約3 KBに減った）。読み込み時はファイル名とメタデータの対応を確かめる。

メタデータ全体はRAMに保持する。ファイルは一時ファイルを同期してから置換するため、途中で止まっても半端な内容は残らない。複数プロセスからの書き込み排他はまだない。

## 点レコード

展開後の`.points`はリトルエンディアンの固定長レコード列。各スキャンの`stride`でサイズを指定する。ディスク上はチャンクごとの独立したブロックで、メタデータに`offset`、`stored_bytes`、`codec`を記録する。

`zstd_shuffle`ブロックは、同じbyte位置を全点から集めた列に可逆転置し、Zstd level 1の独立フレームで圧縮する。フレームのチェックサムを有効にする。点順序もIEEE浮動小数点のbit列も変えない。圧縮で容量が増えるブロックは`raw`で保存する。展開サイズは点数とstrideから計算し、最大32 MiBに制限する。

| オフセット | サイズ | 内容 |
| ---: | ---: | --- |
| 0 | 24 | 描画・計算用ローカルXYZ、f64×3 |
| 24 | 4 | 描画用RGBA、u8×4 |
| 28 | 1 | 座標が有効なら1、無効なら0 |
| 29 | 3 | 予約領域 |
| 32 | schemaによる | 元の数値属性、prototype順 |

元の属性はSingleをf32、Doubleをf64、IntegerおよびScaledIntegerをi64で保存する。ScaledIntegerはscale適用前の整数を保存し、scale/offsetはE57 templateから復元する。属性の削除・量子化は行わない。球面座標は描画用XYZに変換しても、元の球面属性を別に保持する。座標無効レコードは表示しないが、表示中のレイヤーにあれば書き出す。

チャンクはファイルのbyte offsetと点数で参照する。一度作った原解像度点は編集で更新せず、`PointRef = (dataset UUID, chunk index, index in chunk)`を暗黙の識別子として使用する。

LAS/LAZでは現在保持するXYZ・強度・RGBからE57用schemaを作る。その他のLAS属性の保持は別途実装が必要。

## 空間分割とLOD

入力をストリーミングで一時ファイルに書き、外部メモリの再帰的8分割で空間チャンクへ再配置する。分割ごとに中間ファイルを処理し、チャンクが点数・byte数の上限に収まったら確定する。同一点の大量重複や分割深度の上限では、一定点数のファイル区間に分ける。こうしたノードの子数は8に限定されない。

原解像度点はleafにだけ格納する。内部ノード・leafには別の代表点LODを格納する。チャンクと点インデックスのhashが小さい点を選び、子の代表点を親で再選択する。代表点は原解像度点への参照を持つため、点の所属レイヤーを共通に適用できる。

### 並列取り込み

PotreeConverterのタスクプールと書き込み待ち量の制御を参考に、E57の点属性変換とleafのLOD生成・圧縮を並列化している。新しい外部依存は追加せず、Rust標準ライブラリのスレッドとchannelを使用する。既定は利用可能CPU数−1、最小1・最大8ワーカー。`ImportOptions.worker_threads`で1〜64を明示指定でき、0は自動選択。

E57の読み出しは一つのreaderで行い、最大8,192点のraw値バッチをワーカーへ渡す。ワーカーが元の数値属性と描画用XYZ/RGBAを変換し、取り込み順に一時ファイルへ書く。複数スキャンの処理、E57の圧縮データ読み出し、LAS/LAZの点読み出しは引き続き直列。

空間分割は順序を管理するスレッドで行い、leafのchunk/node IDを確定してからワーカーへ渡す。各ワーカーがハッシュ上位K点の選択と点・LODブロックの圧縮を行う。全点をソートせず、必要なK点だけを選択してソートする。完成ブロックは投入順に一つのwriterへ書くため、同じ取り込み設定ならワーカー数で点順序・点参照・LODサンプルは変わらない。

処理中の入力、圧縮scratch、結果バッファーに見積もり容量を予約し、既定256 MiBの`worker_memory_bytes`と最大`2 × ワーカー数`の投入件数で制限する。完成済み結果もwriterが取得するまで予約を維持する。予算が小さい場合はrawバッチを小さくし、極端に属性の多い点では原解像度チャンクも予算に収まるまで小さくする。予約はアクティブなワーカー用変換バッファーの上限であり、アプリ全体のRAM上限ではない。reader・Zstd内部状態、スレッドstack、allocatorの保持領域、親LODの作業領域、manifest、表示キャッシュなどは別途使用する。

leafの書き込み完了後、親LODをディスク上の子LODから逆順に構築する。全ノードの代表点をRAMに保持しない。親LODの構築と空間分割・ファイル書き込みは直列で、分割の一時ファイルI/O削減と空間サブツリー単位の並列化は今後の改善候補。

ワーカー待ちは50msごとにキャンセルを確認し、終了時には未開始タスクを破棄して動作中のワーカーをjoinする。属性変換・分割・親LOD構築にもキャンセル確認を入れている。Zstd呼び出しは一つの最大32 MiBブロックを完了してからキャンセルを確認する。取り込みの確定は全ワーカー完了後なので、途中キャンセル・ワーカーエラーでは元のリビジョンを維持する。キャンセルされたstaging資産は既存の方針どおり残る。

参照した箇所は`ref/PotreeConverter/Converter/src/chunker_countsort_laszip.cpp`の入力バッチ処理、`src/indexer.cpp`のチャンク単位処理、`include/ConcurrentWriter.h`の書き込み待ち容量制御。今回の実装では既存の「leafに全点、別資産に代表点LOD」という形式を維持している。

### LODと表示

`.lod`の展開後の1レコードは36 byte。ノードごとに点と同じ方式で独立圧縮し、`lod_offset`、`lod_bytes`、`lod_codec`を記録する。

| サイズ | 内容 |
| ---: | --- |
| 4 | chunk index、u32 |
| 4 | index in chunk、u32 |
| 24 | ローカルXYZ、f64×3 |
| 4 | RGBA、u8×4 |

表示時はfrustumと見かけの大きさを使ってノードのfrontierを選ぶ。候補を優先度キューで管理し、ノード展開ごとのfrontier全走査を避ける。各ノードに描画枠を残し、枠が十分ならleafの原解像度点を表示する。

デスクトップの表示ワーカーは、展開と非表示レイヤーの点の除外が済んだノードを、スキャンのローカル座標でLRUキャッシュに保持する。既定の上限は256 MiBで、カメラやスキャンの変換だけが変わったときは再利用する。プロジェクト、適用するラベルパッチの一覧、表示中のレイヤーの集合のどれかが変わると無効化する。

移動中は描画上限の1/8（32,000〜300,000点）のLODを要求し、カメラが150ms静止したら設定点数まで詳細化する。移動中の要求はカメラが変わっても完了結果を利用できるため、キャンセルの繰り返しで表示更新が止まることを防ぐ。プロジェクト／リビジョン／表示対象の変更では古い結果を破棄する。

GPU転送前に取得時のカメラ付近の原点を引き、f32の相対座標にする。この原点はカメラだけの移動では変更せず、描画行列で差を吸収する。GPUの点バッファーは容量内なら再利用する。

GPUへのノードごとの常駐管理とLOD再構築はまだない。大量の点を非表示のレイヤーへ移した後にLODの代表点がなくなる問題は、今後の再構築で対応する。

## レイヤー、pose、リビジョン

すべての点はちょうど一つのレイヤーに属する。レイヤーは状態（リビジョン・作業状態）ごとの`layers`に、番号`code`（u8）・名前・表示の有無として記録する。番号0は既定のレイヤーで、常に存在し、改名・削除できない（名前`Points`は画面では「点群」と表示する）。新しいレイヤーには未使用の最小の番号を割り当てる。表示中のレイヤーの点だけを表示・選択・フィルター・位置合わせ・書き出しの対象とし、どのレイヤーにも定義されていない番号の点は非表示として扱う。

点の所属は、チャンクごとに点1つにつき1 byteのレイヤー番号の配列（ラベル）で持つ。`.labels`はラベル配列をチャンクごとに独立したZstd level 3のフレーム（チェックサム付き）で並べたファイルで、その`.json`（ラベルパッチ）がdataset UUID・chunk index・byte offset・長さと、既定以外のレイヤーごとの点数を、スキャン・チャンクの順に持つ。全点が既定のレイヤーに戻ったチャンクは長さ0のブロックとして記録し、配列を持たない。

状態の`labels`は適用するラベルパッチのUUIDを適用順に並べる。チャンクのラベルは、一覧を後ろから見て最初にそのチャンクを含むパッチの配列とし、どのパッチにもないチャンクは全点が既定のレイヤーにある。ラベルパッチは一度書いたら変更しない。点を移す操作（範囲選択、3Dボックス、間引き、ノイズ除去、SOR、レイヤー全体の移動・削除）は、所属が変わったチャンクだけの新しい配列を一つのパッチとして`staging/`に書き、`labels/`へ移してから作業状態の`labels`に追加する。何も動かなかった操作は状態を変えない（レイヤーの削除だけは、点がなくてもレイヤーの定義を外す）。操作が新しく作るレイヤーは非表示で始まり、ユーザーが作るレイヤーは表示で始まる。

チャンクごとのレイヤー別点数はパッチのメタデータにあるため、どのチャンクに非表示の点があるか、レイヤーごとの総点数、表示の描画枠に使う残存割合は、ラベル配列を読まずに求める。非表示の点がないチャンクのラベルは読まない。

操作の記録（`operation`の各要素）には、点を移した操作では移動先のレイヤー番号`target`と移した点数`moved`を加える。

各リビジョンは親ID、対象スキャンID、レイヤーの定義、適用するラベルパッチのID、追加剛体変換、フォルダー（`groups`: ID・名前・親フォルダー）、スキャンの所属フォルダー（`scan_groups`）、操作内容、保存日時（`saved_at`、Unix秒）を持つ。`transforms`はスキャンとフォルダーの両方の追加変換を持ち、スキャンの世界座標は「上位フォルダーから順の変換 × スキャン自身の変換 × スキャンpose × ローカル座標」で求める。

編集は`manifest.draft`（未保存の作業状態）だけを変更し、編集ごとに`project.json`へ書き込む。作業状態は保存済みリビジョン`current`を親とし、編集ごとに新しいIDを持つ（表示キャッシュとプレビューの鍵）。`operation`は`{"kind":"edits","operations":[...]}`で、編集の記録を順に持つ。ユーザーが保存すると作業状態をそのままリビジョンとして追加し、`current`にする。リビジョンを切り替えると作業状態を破棄する。元に戻す・やり直すは、作業状態のスナップショットを差し替えるだけで、点・LOD・ラベルは書き換えない。

取り込みと点の移動は新しい資産を書き終えてから作業状態を更新する。保存に失敗した資産やキャンセルされた作業は未参照のまま残り、「履歴のクリーンアップ」（`Project::cleanup`）で削除する。クリーンアップは保存済みリビジョンと作業状態のどれからも参照されないスキャン・画像情報・ラベルパッチをメタデータから外して保存した後、`data/`の未参照の取り込みディレクトリと未参照の`.points`・`.lod`、`labels/`の未参照のパッチ、`staging/`の中身、中断された保存の一時ファイルを削除する。途中再開、複数リビジョンの集約、積み重なったパッチを一つにまとめる処理は未実装。

スキャンの世界座標は`追加変換 × 元のscan pose × ローカル点`。対応画像は`追加変換 × 元のimage pose`で書き出す。画像をスキャン原点と同一視せず、複数カメラの異なるposeを保持する。
