# 現形式での大規模点群検証（2026-10-04）

## 条件

Windows、Core i5-12400F、RAM 64 GB、RTX 3060、Rust 1.99.0のReleaseビルド。既存の合成LAS（10スキャン×1,000万点、計1億点）を、新しい形式バージョン1のプロジェクトへ取り込み直した。入力ファイル・既存プロジェクトは変更していない。現形式のレイヤーとLAS属性保持を使用し、フィルター予算は既定768 MiB、表示予算は200万点。

測定用プロジェクトは`work-data/review-syn100m-20261004`、連続処理ログは`work-data/review-syn100m-20261004.jsonl`。入力LASの総容量は2.60 GB、取り込み直後のプロジェクトは5.55 GB。取り込み中のstaging容量の観測ピークは2.28 GB。1ファイル分のスプールと空間分割用データが重なるため、完成プロジェクト以外にも一時容量が必要。

工程のRAMはプロセスのワーキングセットを50ms間隔で観測した値。短い工程の真のピークは見逃し得る。初期表示だけは、別プロセスの`view_bench`でOSの累積ピークも取得した。allocatorが保持するメモリがあるため、後の工程のRAMには前の工程の影響が残る。連続処理の測定中にはビルド・テストが同時実行された時間があり、時間はこのセッションでの参考値で、旧版との厳密な速度比較ではない。ディスクキャッシュや他の処理でも変わる。

## 連続処理

| 工程 | 経過時間 | RAMの観測ピーク |
| --- | ---: | ---: |
| 取り込み（1億点） | 253.0秒 | 92.0 MiB |
| 初期表示（CPU読み込み、約199万点） | 44.5ms | 93.7 MiB（別プロセスのOSピーク） |
| 2cmボクセル間引き | 47.1秒 | 297.7 MiB |
| Undo/Redo、20往復（40回の状態復元） | 0.420秒 | 29.8 MiB |
| ノイズ除去、半径5cm・4点未満 | 36.0秒 | 229.5 MiB |

間引きで70,418,560点、ノイズ除去で6,087,296点を別レイヤーへ移し、残り23,494,144点を書き出した。LASは約611 MB、LAZは約265 MB。Undo/Redoの後の状態IDが編集後の状態IDと一致することを検証した。

編集後のCPU表示更新は、初回707.8ms、p50=4.19ms、p95=5.96ms、p99=7.53ms。初回は非表示マスクの読み込みも含み、キャッシュが温まるまでの時間が掛かる。最後の視点では約174万点、表示キャッシュ合計117.6 MB、そのうち非表示マスク等11.9 MB。これらはGPU転送・描画・画面提示を含むフレーム時間ではない。

初期表示の別プロセスによるログは`work-data/review-syn100m-initial-view-20261004.log`。2回目以降の近い視点では約2〜3msで、原解像度の全点をRAMへ展開せず表示できた。

## GUIの2分間の表示

同じ編集済みプロジェクトをRelease版で開き、カメラを120秒間回転・平行移動した。平行移動は対象付近を往復する経路で、点群から離れ続けない。GPUはDX12、スクリーンショットのサイズは1,920×1,008 pixel。点サイズ2、EDL有効、描画予算200万点。開始直後の1秒を除くUI callback間隔を記録した。

| --- | ---: |
| UI callback間隔のサンプル数 | 7,140 |
| p50 | 16.68ms |
| p95 | 17.86ms |
| p99 | 18.94ms |
| カメラ移動中に完了した表示更新 | 2,938回 |
| 最終表示点数 | 1,734,030点 |
| GUIのワーキングセットの観測ピーク | 461.8 MiB |
| GUIのPrivate Memoryの観測ピーク | 874.0 MiB |
| 専用GPUメモリの観測ピーク | 452.0 MiB |
| 共有GPUメモリの観測ピーク | 226.7 MiB |

終了コード0、エラー通知なし、スクリーンショット保存まで確認した。RAM・GPUメモリは約500ms間隔の観測値。専用・共有GPUメモリはWindowsの`Win32_PerfFormattedData_GPUPerformanceCounters_GPUProcessMemory`で対象pidのインスタンスを合計した値で、アプリの点バッファーだけではなく描画先・ドライバー等も含む。Private Memoryは常駐RAM量とは別の指標。UI callback間隔はGPU fenceやモニターへの提示を直接測定した値ではないため、これを厳密なGPUフレーム時間とは呼ばない。

ログ・metrics JSON・PNGは`work-data/review-syn100m-gui-bounded-20261004.*`。最初の長時間検証では従来の一方向の平行移動により対象から外れ、スクリーンショット検証が完了しなかった。その試行の値は採用せず、経路を修正した後の完走した試行を記録した。

## 再現手順

既存の合成入力がなければ、最初に`make_synthetic`で作る。`workflow_bench`の出力プロジェクトは未作成のパスを指定する。

```powershell
cargo run -p geemil-core --release --example make_synthetic -- work-data/syn100m-new 10 10000000
cargo run -p geemil-core --release --example workflow_bench -- work-data/bench-current work-data/syn100m-new 1200
cargo run -p geemil-core --release --example view_bench -- work-data/bench-current 2000000 0 Imported
```

`view_bench`の最後の引数は保存済みリビジョンの名前で、メモリ上でその状態を参照する。プロジェクトのリビジョンをディスク上で切り替えない。新版の測定ヘルパーは50msの工程別サンプルに加え、短い工程でもピークを確認できるようにプロセス起動からのOS累積ピークを出力する。

GUIのRAM・GPUメモリとUI callback間隔を記録するには、PowerShell 7で以下を実行する。GPUカウンターへのアクセスができない環境ではGPUメモリはnullとなる。

```powershell
cargo build -p geemil-desktop --release
.\scripts\measure-gui.ps1 -Project work-data/bench-current -OutputPrefix work-data/bench-gui -OrbitSeconds 120 -PointBudget 2000000
```

## 検証の範囲

合成シーンは地面・円形の壁・規則的な箱で、実データ全般を代表しない。非常に大きな探索半径や極端な密集では、ノイズ除去・SORの分割探索が時間を要する。分割探索の正しさは小規模データの通常探索との一致、重複点、非表示点、チャンク境界、キャンセルで検証した。今回の1億点の連続処理にはSORは含めていない。

旧版の実測と比較して遅い工程もある。点の属性・表示構造・メモリ制御が異なるため、今回の結果を高速化率として扱わない。リソース予算はアプリ全体の厳密なRAM上限ではなく、メタデータ・表示・圧縮ライブラリ内部・allocator等は別に使用する。
